# Triage, ownership, and follow-through

**Proposed demonstration playbook.** This describes how I would organize support for Sample Planning Workspace, the fictional application used in this portfolio.

## Keep one reliable request record

For each request, capture the requester and organization, user goal, affected workspace, category, impact, scope, start time, evidence, owner, next action, and next-update time. Record the expected result separately from the observed result.

Use timestamps with time zones. Distinguish customer-reported facts from support observations and hypotheses.

## Classify the work

| Category | Example | First route |
| --- | --- | --- |
| How-to or training | User cannot find the right planning scenario | Support guidance and a linked article |
| Access request | Approved user needs workspace membership | Authorized owner/administrator approval |
| Incident | Previously available application function stops working | Support investigation and engineering when needed |
| Data correction request | Authorized owner reports an incorrect source record | Data owner review and controlled correction |
| Product feedback | Several users request clearer report context | Clarify the need and document a product proposal |

A report can change category as evidence develops. Preserve that history.

## Prioritize by impact and scope

A broadly unavailable service, a single blocked user, and a cosmetic issue have different urgency. Ask whether a deadline is affected, whether there is a verified workaround, and how many users or business tasks are blocked.

Apply the employer's actual severity definitions, response targets, business hours, and escalation paths. Do not invent a contractual deadline or describe a next-update commitment as a resolution guarantee.

## Use explicit states

**New:** Not yet assessed.  
**Investigating:** Support has an owner and an action in progress.  
**Waiting for customer:** A specific missing detail has been requested, with a follow-up date.  
**Waiting for engineering or administrator:** The receiving owner and evidence are linked. Support still owns customer updates.  
**Resolved pending confirmation:** The original task has been retested; customer confirmation is requested.  
**Closed:** The resolution and confirmation, or a documented closure rule, are recorded.

## Escalate with the investigation attached

A useful engineering handoff includes a concise problem statement, environment, reproducible steps, expected and actual behavior, scope, business impact, and minimal permitted evidence. State what has already been checked and what remains unknown. Include a safe workaround only when it has been verified.

For an access change, retain the required approval. For a data change, retain the source owner and correction history.

## Close the loop

Retest the original task, update the customer, link related work, and record the result. A workaround can restore progress while the underlying defect remains open.

Review repeat contacts weekly. Look for unclear guide sections, training gaps, recurring defects, or product needs. Track useful outcomes such as independent task completion, repeat questions on the same topic, reopened requests, and unowned items. Establish a baseline before claiming improvement.

## Responsible use of AI assistance

If organizational policy permits it, an assistant could suggest a category or draft a response from sanitized information. The support owner checks factual accuracy, permissions, and next steps before using the output. This is a proposed workflow, not a claimed prior AI support deployment.
